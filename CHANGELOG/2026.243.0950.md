# 2026.243.0950 — docs: correct a changelog entry that described prose as dependency pins

## Summary

Corrects `CHANGELOG/2026.243.0839.md`, the entry for PR#5, which described a documentation refresh
as an advance of dependency **pins**.

That entry justifies the release with:

> a published tag embeds the pins it carried at tag time, so every consumer that pins a tag of
> this candy drags those old refs into its own resolution, and charly reports them as
> `resolved to multiple versions` on every build of that consumer

**None of that applies.** All 4 refs that release changed live inside
`content:`/`description:` block scalars — usage examples inside skill documents — which charly
parses as opaque strings and never resolves. No dependency edge moved, and none of those refs
ever contributed to a version-skew warning.

The change itself was harmless and remains correct as a documentation refresh. Only its
description was wrong.

## Root cause

The scanner in use when that PR was written matched refs with a plain regex over the whole
file. A YAML example printed inside documentation is textually identical to a real dependency
entry — both render as `  - '@github.com/opencharly/x:vY'` — so it could not tell them apart
and reported documentation strings as stale pins.

It has since been replaced with a block-scalar-aware parser. Under the corrected scanner this
release contains **no** resolving refs at all.

## Empirical confirmation — charly's own behaviour, with a negative control

`:vTAG` is not a resolvable tag, so if these refs were dependency edges, validation would fail
on them. It does not — while it *does* fail for a genuinely resolving ref:

```
control: pod-hermes (5 real resolving refs), one set to :vTAG
$ charly box validate ; echo "exit=$?"
charly: error: command "validate": validation error: downloading
  github.com/opencharly/layer-ffmpeg:vTAG: InvokeProvider refs:refs op=resolve: resolving ...
exit=1
```

charly rejects an unresolvable REAL ref with a hard error, and does not notice prose refs at
all. That is only possible if it never resolves them — demonstrated rather than argued.

## What changed

Two corrections in this entry; everything else in it is accurate and untouched.

1. **The characterisation** — a correction note records what the release actually changed, the
   evidence, and the root cause, directly under the Summary heading.
2. **The attribution tier** — it claimed a RUNTIME tier, which the rulebook forbids here:
   *"Runtime confidence is forbidden for prose-only work."* Corrected to
   `documentation reviewed` in both the tier bullet and the `Assisted-by:` footer.

## How tested

Each ref's enclosing block scalar is identified with its line number, together with the
decisive check — the count of lines between the opener and the ref that would CLOSE the block,
which is zero in every case. Reproducible with `sed -n '<opener>p;<ref>p' charly.yml` against
the commit named below.

This commit edits one changelog file. No content ships, so no candy version is bumped:
correcting a historical record is not a release.

  The scanner was fixed first; this corrects the records it produced, across every affected
  repo rather than the one that surfaced it.

- **R4 (no workarounds)** — the entry is corrected, not annotated with an erratum beside the
  false claim.

- **R6 (git safety)** — feature branch, no force-push, no history rewrite; the published tag
  and its commit are untouched.

  negative control.
