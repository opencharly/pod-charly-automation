# 2026.288.0732 — docs(crabbox-deploy): stop restating the CLI version, and drop a stale validate note

## Summary

Two prose fixes in the `crabbox-deploy` skill entity's owning repo, both of them R1 divergences
between what the repo says and what is true.

**1. The skill restated a CLI version it does not own, and the restatement was stale.**
`charly.yml`'s `crabbox-deploy-skill` Quick Reference carried:

```
| CLI version | `crabbox --version` | Verified 0.48.1 pin |
```

The pinned CLI has been **0.51.0** since `layer-crabbox` v2026.250.1023 and is now **0.78.0** —
twenty-seven releases on — so the row was already false when it was written, relative to the
release it named. It matters beyond tidiness because this entity is the projection **source**:
the marketplace corpus (`marketplace/automation/skills/crabbox-deploy/SKILL.md`) and the docs
mirror plus the generated recipe page are all rendered from it, so one stale row made three
published copies untrue.

The fix is deliberately **not** a fresh version literal, which would drift again the next time
the pin moves. The version has exactly one home — `layer-crabbox`'s `CRABBOX_VERSION` — and the
row now says so and says not to restate it here.

```diff
-| CLI version | `crabbox --version` | Verified 0.48.1 pin |
+| CLI version | `crabbox --version` | The pin is owned by `layer-crabbox`'s `CRABBOX_VERSION` — never restate a version here |
```

**2. The repo's own `AGENTS.md` documented a check failure that no longer occurs.** Its
"Build / validate / test" section carried a note that the manifest was stamped `2026.249.2125`
while the pinned charly required `2026.261.1747`, "so the check fails with `Run: charly migrate`".
Neither stamp is in the manifest and the check is green, so the note was false. A stale note that
tells the next session to expect a failure is worse than no note: it invites a `charly migrate`
against a manifest that does not need one.

```diff
-- `charly box validate` at the repo root — the structural check: the manifest
--   must parse and validate at the installed charly. NB: the repo's current
--  `charly.yml` is stamped `2026.249.2125` while the pinned charly requires
--  `2026.261.1747`, so the check fails with `Run: charly migrate` until that
--  separate schema-stamp cutover lands; it is unrelated to a docs-only change.
+- `charly box validate` at the repo root — the structural check: the manifest
+  must parse and validate at the installed charly. It is green (checked 1 candy,
+  7 distros, 7 builders; 0 warnings, 0 errors), so it is the gate a docs-only
+  change runs.
```

**Not in this change, deliberately.** The corpus projection of the corrected row needs the
marketplace refs to move to a tag carrying this commit, which is the automated refs refresh
(opencharly/marketplace#447 — I added the evidence there rather than opening a competing refs
PR, which R2 forbids). Producer-first order: this repo's entity, then merge, then tag, then the
refresh projects it.
